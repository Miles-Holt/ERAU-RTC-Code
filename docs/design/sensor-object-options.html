Front Panel Object System

One way of drawing every object on the panel, and one way of commanding it. A sensor, a valve and a state machine are the same construction — an optional glyph, a name line and a line of live text — so the panel reads as one instrument rather than three widget families. Everything is drawn at true size in the app's own palette.

Three things to pick — everything else is settled
  1. The bubble interior A empty · B whole tag · C type set large · D drawn mark per instrument type Decides whether the tag is read inside the circle or off the name line.
  2. The command panel layout 1 segmented control · 2 action list Both open under the cursor and both stay open; they differ in whether the states sit side by side or stack as verbs.
  3. The state-ring interior mark one mark for every machine · a mark per state, set in the editor Per-state reads faster once learned and is one more thing to author per machine.

Thirteen changes from your annotations are already applied below — the bubble has no centre line, the name line is the title, unbound is grey, alarm is a thickened ring and nothing else, abort is an ordinary state, mismatch is an alert rather than a look, and selection is a glow that layers under the object. Rather than list them, the permutations are drawn.

COMMAND

The dropdown, rebuilt around the click count

pick one

Today: click the valve, the panel opens centred on the object, you travel to a small Open button, and any click outside dismisses it unless you hit Pin first (valveDropdown.js). Toggling twice is four clicks and a mouse race. The panel concept stays. Four things change, and they are what kill the race:

  • Commands come first — the command control is the top of the panel, not a row buried in the channel list.
  • It opens under the cursor, with the command control on the pointer. No travel to the first click.
  • It stays open until you dismiss it with Esc, the ✕, or a click on the canvas. Pin disappears — sticky becomes the default rather than an opt-in you have to reach for first.
  • The next click is in the same place. Open then closed then open is three clicks that never move the mouse, because the control does not relayout when the state changes.

Each stage below is a valve sitting on the panel grid with its menu open, drawn where it actually lands: under the cursor, over the object. The pointer mark is the click that opened it.

A state machine gets the same panel instead of the native <select>: one row per state, the current one marked, and — the part the <select> could never show — targets blocked by operator from … gating are drawn dimmed with the reason, instead of being silently accepted and refused by the server.

EDITOR

The problem list

editor only

Unbound renders as unbound on the canvas and reaches no list at all today. The warnings button in the editor header is fed from exactly one place — routingErrors.push in editor.js, on a pidRoute failure — so it is a routing list, not a problem list. A broken channel binding does not appear in it either; it is simply invisible until you notice the object is grey.

So the change is wider than adding one entry: the button becomes a problem list rather than a routing list. One flat list, no severities — a routing failure and an unbound binding are both a location plus a one-line reason, and sorting them into buckets would add a decision to every row without changing what any row says. One list, one count on the button, every row clickable back to the offending element — which is the part that makes a list worth opening.

Worth saying plainly: this is a drawing check, not a config check. It catches a layout that references a control the config does not have — a renamed refDes, a copied object, a panel drawn against a different stand. It cannot tell you the config itself is wrong.

ALERTS

One path to red

runtime change

The change you called: the broker stops being a second source of truth. Today broker.checkBounds emits bad_data on every validMin/validMax crossing, and the alert template separately raises a row off the same event — two mechanisms, one fact. After the change there is one: an alert template auto-generated for every sensor channel. Out of range still shows on the object, because the object colours from the raised alert like everything else does.

FactTodayAfter
CPT-01 above validMax bad_data from the broker colours the reading; the template separately raises a warning row One auto-generated sensor alert raises. The object colours from it. One event, one row, one reason.
Valve commanded open, feedback shut Red ring, indistinguishable from a comms fault Templated valve not responding to command alert; object goes red with the reason in words
Node reconnects on reconnect -> info raises a fresh info row Line removed. The disconnect alarm goes inactive and stays on the board until reset.

One thing to know about that last row, because the code does not quite say what the config implies: Registry.Clear() does not delete an alert, it sets Acked = true and broadcasts alert_acked — and the browser keeps acked rows in the list, greyed, out of the unacked count. So removing the reconnect line gives you exactly the behaviour you described. It also means the server acks the disconnect on your behalf: no operator ever has to acknowledge that a node dropped. If that ack should be a human's, Clear is the wrong verb on the reconnect path and wants a separate resolved-but-unacked state. Flagging it, not changing it.

DECISIONS

Where this stands

Loudness of a configured alarm
Static thickened ring. No pulse, no marker dot. Your call: "i like what it is now".
Ring as a gauge sweep
Not for sensors. Kept for valve position, on its own outer ring, with limit-switched feedback drawn as discrete ticks rather than a sweep.
Valve command/feedback mismatch
Not a distinct visual. A templated valve not responding to command alert, which turns the object red — your call, and it means a stuck valve and a dead link now differ in the alert bar rather than in a glyph a reader has to decode.
The bad_data path
Removed from the broker; replaced by an auto-generated alarm template across all sensor channels. Out of range stays visible.
