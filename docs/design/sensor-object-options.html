Front Panel Object System

One way of drawing every object on the panel. A sensor, a valve and a state machine are the same construction — an optional glyph, an optional title, and a line of live text — so the panel reads as one instrument rather than three widget families. Everything is drawn at true size in the app's own palette.

Your notes, applied
  • Inline is the base. No box. The glyph and the title are both opt-in per object.
  • The status dot is gone. State is carried by the colour of the reading itself, and by the glyph's ring when a glyph is present.
  • Out of range is visible, not loud — the number turns red and the ring turns red. Nothing moves, nothing flashes.
  • Alarm is the loud state, and only a configured alert can raise it. Nothing auto-alarms from validMin/validMax: those are plausibility bounds on a system that is not live yet, so a blanket rule would cry wolf from day one. This also means dropping the blanket on bad_data line from the every-daqNode alert template — a config change, noted below.
  • No sparkline.
  • The glyph is the family resemblance: an instrument balloon for a sensor, the valve symbol for a valve, a state ring for a machine — same circle, same ring, different interior.

The same sensor, four ways

per-object toggles

Glyph and title are independent switches, so a panel can carry dense readings in the corner and fully labelled instruments where it matters — without two renderers.

SENSOR

Instrument balloon

glyph Ø 34

The ISA 5.1 balloon: tag split across a centre line. The ring carries data quality; the number carries the value. Shown here with glyph and title on, which is the loudest the sensor gets.

VALVE

Valve symbol

glyph Ø 34 — same ring

Same circle, same ring semantics, valve symbol inside: the line lies across the bore when shut and along it when open, with an arc and pointer for a percentage feedback. The text line reads the commanded state rather than a number.

STATE MACHINE

State ring

glyph Ø 34 — segmented

The ring is divided into one segment per state, with the current one lit — so position in the sequence is readable at a glance, before you read the word. The text line names the state; the operator's target dropdown sits below it as it does today.

DECISIONS

Still yours to call

01How loud is "loud" for a configured alarm?
Drawn here as a thickened ring plus a filled marker — static. The step up from that is a slow pulse, which is genuinely impossible to miss across a room and genuinely irritating if it sits unacknowledged for an hour. Say which and I will build it.
02Should the ring double as a range indicator?
The ring is currently a status colour only. It could instead sweep like a gauge — filling as the value crosses its band — which reads well for a pressure and means nothing for a thermocouple. Cheap to add later; awkward to retrofit if the ring already means three other things.
03Valve: is the mismatch state worth its own look?
Commanded open, feedback says shut — today that shows as a red ring, identical to a comms fault. They are different problems: one is a stuck valve, the other is a dead link. I would give the stuck valve its own mark, but it costs a distinct visual that has to stay legible at 34 px.
04Confirm the alert-template change.
Per your note, I will drop on bad_data -> warning from the every-daqNode template in config/alerts/alerts.alert, so out-of-range readings stop raising automatic alerts and only explicitly written rules do. Disconnect, reconnect and stale stay as they are.
